# Autonomous Contract Document Agent

Автономный ИИ-агент для анализа договорных документов и дополнительных соглашений.

Система принимает набор PDF-документов, извлекает из них структурированную информацию, связывает дополнительные соглашения с основными договорами, формирует договорные цепочки, группирует договоры по предмету и позволяет через естественный язык получать информацию об истории изменений и текущих структурированных условиях договора.

Проект реализован как **tool-using agent**, а не как фиксированный pipeline запрос → LLM → ответ.

---

## 1. Что умеет система

Агент умеет:

* анализировать PDF-документы;
* определять тип документа:

  * основной договор;
  * дополнительное соглашение;
  * завершающий документ;
  * иные документы;
* извлекать идентификаторы договоров;
* связывать дополнительные соглашения с основными договорами;
* формировать договорные цепочки;
* извлекать изменения из дополнительных соглашений;
* агрегировать изменения в структурированное текущее состояние договора;
* показывать историю изменений;
* группировать договоры по типу и предмету;
* сравнивать несколько договоров по доступным структурированным условиям;
* показывать предупреждения о неполноте извлечения;
* самостоятельно выбирать необходимые инструменты в зависимости от запроса пользователя;
* выполнять дополнительную проверку сформированного ответа через Reflection.

# 4. Основные компоненты

## 4.1 PDF Parser

`app/services/pdf_parser.py`

Извлекает текст из PDF с сохранением информации о страницах.

Результат используется extractor'ом для:

* анализа структуры документа;
* определения метаданных;
* извлечения изменений;
* сохранения номера страницы источника.

---

## 4.2 Extractor

`app/services/extractor.py`

Extractor выполняет два этапа:

1. извлечение метаданных документа;
2. извлечение изменений по страницам.

Для больших документов текст разбивается на перекрывающиеся chunks.

Текущие параметры:

```python
CHUNK_PAGES = 8
OVERLAP_PAGES = 1
```

Для structured output используется LLM.

Extractor извлекает, в частности:

```text
document_type
document_id
contract_id
referenced_contract_id
contract_number
document_date
effective_date
contract_type
subject
parties
changes
```

Для изменений:

```text
section
section_context
change_type
description
old_value
new_value
old_text
new_text
source_page
```

### Типы изменений

Поддерживаются:

```text
add
modify
delete
replace_section
```

---

## 4.3 Validator

`app/services/validator.py`

Выполняет минимальную структурную валидацию результата extraction.

Например, для основного договора требуется наличие:

```text
document_type
document_id
contract_id
```

Для дополнительного соглашения:

```text
document_type
document_id
referenced_contract_id
```

Статус обработки может быть:

```text
success
partial
rejected
```

`success` означает успешное прохождение структурной обработки, но не гарантирует идеальную семантическую полноту извлечения.

# 5. Договорные цепочки

`app/services/contract_chain_builder.py`

После extraction документы связываются в договорные цепочки:

```text
Основной договор
       │
       ├── Дополнительное соглашение №1
       │
       ├── Дополнительное соглашение №2
       │
       └── Дополнительное соглашение №3
```

Например:

```text
D200262543-01
│
├── D230166734-01
├── D240114026-01
└── D240128432-01
```

Связь определяется по `contract_id` / `referenced_contract_id`.

Если основной договор отсутствует в наборе, цепочка помечается как:

```text
incomplete
```

с соответствующим предупреждением.

# 6. Свёртка договора

Под "свёрткой" в проекте понимается не реконструкция полного юридического текста договора.

Вместо этого система формирует структурированное представление:

```text
Основной договор
      │
      ▼
История дополнительных соглашений
      │
      ▼
Извлечённые изменения
      │
      ▼
Попытка применить изменения
      │
      ├── applied
      │
      └── failed
      │
      ▼
Текущее структурированное состояние
```

Основными результатами являются:

### `history`

История изменений:

```text
какое соглашение
когда
какой раздел
какое изменение
на какой странице
```

### `current_conditions`

Структурированное текущее состояние тех условий, которые удалось агрегировать.

### `replacements`

Информация о случаях, когда изменение представляет замену целого раздела / приложения и не сводится к простой паре `key → value`.

### `warnings`

Информация о неполноте или невозможности применить отдельные изменения.

---

## Важное различие

Извлечение изменения и его применение к структурированному состоянию — это разные операции.

Например:

```text
change extracted
       │
       ▼
attempt to apply
       │
       ├── applied
       │
       └── failed
```

Если изменение не удалось применить, это **не означает, что оно не было извлечено**.

Оно остаётся в `history`, а в `warnings` появляется информация о невозможности применения.

Это позволяет не терять информацию из исходного документа.

# 7. Кластеризация

`app/services/clusterer.py`

Текущая реализация использует **детерминированную группировку**, а не embedding-based clustering.

Ключ группы:

```python
(contract_type, subject)
```

Таким образом, документы с одинаковым типом договора и одинаковым предметом попадают в одну группу.

Например:

```text
cluster_1
    contract_type = ...
    subject = ...
    contract_ids = [...]
```

Такой подход выбран как простой и воспроизводимый способ группировки на текущем наборе документов.

Это **не является ML-кластеризацией** и не позиционируется в проекте как semantic clustering.

# 8. Agent

`app/agent/agent.py`

Агент построен на LangChain и использует набор инструментов.

Доступные tools:

```text
get_extraction_issues
get_contracts
get_contract_history
get_contract_clusters
compare_contracts
compare_cluster_contracts
get_cluster_details
```

Агент самостоятельно выбирает необходимые инструменты в зависимости от пользовательского запроса.

Например:

```text
"Покажи договорные цепочки"
        │
        ▼
get_contracts
```

А:

```text
"Какие изменения были внесены в D210262441-01?"
        │
        ▼
get_contract_history
```

А:

```text
"На какие группы распределены договоры?"
        │
        ▼
get_contract_clusters
```

# 9. Reflection

После генерации ответа выполняется дополнительная проверка.

Reflection проверяет, в частности:

* отвечает ли ответ на исходный запрос;
* существуют ли упомянутые document ID;
* не смешаны ли данные разных дополнительных соглашений;
* соответствуют ли утверждения результатам tools;
* учитываются ли предупреждения;
* не выдуманы ли отсутствующие значения;
* различается ли история изменений и текущее состояние;
* учитываются ли не применённые изменения;
* не делается ли вывод о текущем состоянии только на основании `history`.

При обнаружении проблемы агент может сгенерировать ответ повторно с учётом замечаний Reflection.

# 10. Запуск

Установить зависимости:

```bash
uv sync
```

Подготовить переменные окружения / конфигурацию LLM согласно `app/config.py`:
API_KEY=...
FOLDER_ID=... (для YANDEXGPT; иначе убрать или оставить пустым)
BASE_URL = ...
MODEL = ...

Затем запустить положить документы в `data/input` и запустить препроцессинг:

```bash
uv run main.py
```

Последний сформирует `documents.json`, содержащий информацию о документах.
Интерактивно работать с информацией о документах можно, запустив:

```bash
uv run agent_main.py
```

После запуска:

```text
Contract Agent
Введите 'exit' для выхода.
```

Далее можно задавать вопросы на естественном языке.

# 13. Свёртка конкретного договора

Один из наиболее показательных примеров — договор:

```text
D210262441-01
```

Основной договор:

```text
D210262441-01
```

Дополнительное соглашение:

```text
D250134282-01
```

Предмет основного договора:

```text
установление дополнительных обязательств Партнера
по выполнению плановых показателей на Торговых точках
и выплата дополнительного вознаграждения
```

Дополнительное соглашение действует с:

```text
01.06.2025
```

Агент может получить эту информацию через:

```text
get_contract_history("D210262441-01")
```

### Результат

В результате агрегирования формируются:

```text
current_conditions
history
warnings
replacements
```

Например, для данного договора система фиксирует историю изменения и одновременно предупреждает, если отдельные изменения не удалось применить к структурированному состоянию.

### Комментарий

Это демонстрирует основную идею свёртки:

```text
основной договор
      +
дополнительные соглашения
      ↓
единая структурированная история
      ↓
актуальные структурированные условия
```

При этом исходный юридический текст договора не переписывается целиком.

# 14. Сравнение договоров

### Запрос

```text
> Сравни договоры D200262543-01 и D220600738-01
по доступным структурированным условиям.
Укажи, какие условия есть у каждого договора,
какие совпадают, какие различаются,
а также какие замены разделов и предупреждения зафиксированы.
```

Агент выбирает:

```text
compare_contracts
```

Инструмент возвращает для каждого договора:

```text
contract_id
current_conditions
replacements
warnings
history
```

После этого LLM формирует человекочитаемое сравнение.

### В результате для D200262543-01 могут фигурировать, например:

```text
электронный документооборот;
архивирование документов;
права и обязанности;
реестр документов;
контроль соблюдения требований;
обработка персональных данных;
изменения тарифных групп;
изменения приложения №3;
изменения приложения по AutoPay.
```

Для D220600738-01:

```text
продолжение обслуживания абонентов;
каналы уведомления;
механика продвижения;
конвергентные продукты;
изменения соответствующих приложений.
```

### Комментарий

Сравнение выполняется по доступным структурированным данным.

Инструмент не пытается самостоятельно реконструировать полные юридические тексты документов.

# 15. История изменений и текущее состояние

Система сознательно разделяет два типа информации.

## История

`history` отвечает на вопрос:

> Какие изменения были внесены документами?

Например:

```text
D250134282-01
    ↓
изменение X
    ↓
изменение Y
    ↓
изменение Z
```

## Текущее состояние

`current_conditions` отвечает на вопрос:

> Какие структурированные условия сейчас представлены после применения изменений?

Поэтому утверждение:

```text
"условие X является текущим"
```

должно подтверждаться `current_conditions`.

А утверждение:

```text
"в дополнительном соглашении было изменение X"
```

может подтверждаться `history`.

# 16. Частичное извлечение

Некоторые PDF могут обрабатываться частично.

Например:

```text
status = partial
```

означает, что часть chunks документа не была успешно обработана.

В этом случае система сохраняет уже полученные данные, но сообщает о потенциальной неполноте.

Например:

```text
D240114026-01
status: partial
failed_chunks: [4, 5, 8]
contract_id: D200262543-01
```

Другой пример:

```text
Проект Договора.pdf
status: partial
failed_chunks: [4]
contract_id: D200262543-01
```

### Почему это важно

Если документ обработан частично, нельзя делать вывод:

```text
"изменений больше нет"
```

только потому, что extractor их не вернул.

Правильная интерпретация:

```text
известные изменения
+
информация о неполноте
```

---

# 17. Обработка ошибок применения изменений

Не каждое извлечённое изменение удаётся применить к структурированному состоянию.

Например:

```text
D210355320-01

applied = 4
failed = 3
```

Это означает:

```text
7 изменений извлечено
4 удалось применить
3 не удалось сопоставить
```

Неуспешные изменения не удаляются из истории.

Они остаются в:

```text
history
```

и сопровождаются:

```text
warnings
```

Это позволяет отличать:

```text
"изменение не было извлечено"
```

от

```text
"изменение было извлечено,
но не удалось применить его к структурированному состоянию".
```

# 18. Ограничения текущей реализации

## 18.1. Кластеризация

Сейчас используется:

```text
(contract_type, subject)
```

Это детерминированная группировка.

Embedding-based clustering или ML-кластеризация не используется.

---

## 18.2. Полная реконструкция договора

Система не пытается восстанавливать полный актуальный юридический текст договора.

Результат представляет собой:

```text
history
+
current_conditions
+
replacements
+
warnings
```

Это позволяет анализировать историю и структурированное состояние без необходимости генерировать полностью переписанный текст юридического документа.

---

## 18.3. Partial extraction

Качество извлечения зависит от используемой LLM.

В отдельных документах обработка chunks завершалась ошибкой внешнего LLM API / content filter.

Такие случаи сохраняются как:

```text
status = partial
```

и не маскируются под успешную полную обработку.

---

## 18.4. Применение изменений

Structured aggregation не гарантирует применение каждого изменения.

Причины:

* отсутствует соответствующее условие в текущем состоянии;
* условие нельзя однозначно сопоставить;
* идентификатор раздела отличается от извлечённого;
* изменение относится к целому разделу или приложению.

В таких случаях изменение сохраняется в истории и помечается как не применённое.

---

## 18.5. Сравнение договоров

`compare_contracts` предоставляет структурированные данные нескольких договоров.

Финальное человекочитаемое сравнение формирует LLM.

Это позволяет агенту интерпретировать различия в зависимости от формулировки запроса пользователя.

---

# 19. Почему это агент, а не обычный chain

Вместо фиксированной последовательности:

```text
query
  ↓
tool 1
  ↓
tool 2
  ↓
answer
```

используется агентная схема:

```text
User query
    │
    ▼
  Agent
    │
    ├── get_contracts
    │
    ├── get_contract_history
    │
    ├── get_contract_clusters
    │
    ├── get_cluster_details
    │
    ├── compare_contracts
    │
    ├── compare_cluster_contracts
    │
    └── get_extraction_issues
            │
            ▼
       Tool results
            │
            ▼
          Agent
            │
            ▼
          Answer
            │
            ▼
        Reflection
```

Выбор инструмента зависит от пользовательского запроса.

Например:

```text
"Какие договоры есть?"
        ↓
get_contracts
```

```text
"Какие изменения внесены в договор?"
        ↓
get_contract_history
```

```text
"На какие группы разделены договоры?"
        ↓
get_contract_clusters
```

```text
"Сравни D200262543-01 и D220600738-01"
        ↓
compare_contracts
```

Таким образом, tools предоставляют агенту разные операции над одной предметной областью, а LLM выбирает необходимые операции и интерпретирует их результаты.

---

# 20. Итоговый результат

Для пользователя система предоставляет интерфейс на естественном языке:

```text
> Какие изменения были внесены в договор D210262441-01?

> Покажи все договорные цепочки.

> Какие договоры входят в cluster_3?

> Сравни D200262543-01 и D220600738-01.

> Какие изменения не удалось применить?

> Какие договоры были обработаны неполностью?
```

Внутри при этом используются:

```text
PDF parsing
    ↓
structured extraction
    ↓
validation
    ↓
contract chains
    ↓
aggregation
    ↓
deterministic grouping
    ↓
agent tools
    ↓
LLM reasoning
    ↓
reflection
```

Основной принцип проекта:

> **Не заставлять LLM самостоятельно "читать" весь набор документов при каждом запросе, а предоставить агенту специализированные инструменты над предварительно структурированными данными.**

Это позволяет отделить:

* извлечение информации;
* связывание документов;
* агрегацию изменений;
* группировку;
* получение данных;
* интерпретацию;
* контроль качества ответа.
